## M3-1 后台超过 30s 吗 · `lifecycle/Lifecycle.kt`

<details><summary>提示 2</summary>

`backgroundAtMs` 是 `Long?`，先处理 null：`if (backgroundAtMs == null) return false`。之后编译器知道它不是 null 了（smart cast），可以直接相减。正好 30s 也算，用 `>=`。
</details>

<details><summary>答案</summary>

```kotlin
if (backgroundAtMs == null) return false
return nowMs - backgroundAtMs >= THRESHOLD_MS
```
</details>

想一想：
- 为什么 `now` 要作为参数传进来，而不是在函数里调 `System.currentTimeMillis()`？（测试里要造「过了 35s」；前端写单测时你怎么处理 `Date.now()`？）

## M3-2 进程级生命周期事件 · `lifecycle/Lifecycle.kt`

<details><summary>提示 2</summary>

```kotlin
when (event) {
    Lifecycle.Event.ON_STOP -> backgroundAtMs = now()
    Lifecycle.Event.ON_START -> {
        // 问 RefreshPolicy；要刷新就 log + onRefresh()
        // 不管刷不刷新，backgroundAtMs = null
    }
    else -> {}
}
```

`when` 当语句用（不要它的值）时可以不写全，但这里有 `else -> {}` 更清楚。
</details>

<details><summary>答案</summary>

```kotlin
when (event) {
    Lifecycle.Event.ON_STOP -> backgroundAtMs = now()
    Lifecycle.Event.ON_START -> {
        if (RefreshPolicy.shouldRefresh(backgroundAtMs, now())) {
            log("后台超过 ${RefreshPolicy.THRESHOLD_MS / 1000}s，刷新列表")
            onRefresh()
        }
        backgroundAtMs = null
    }
    else -> {}
}
```
</details>

想一想：
- 🔬 手动验收（填完 M3-6 后）：回桌面等 35s 再回来，logcat 有 `后台超过 30s，刷新列表`，mock 服务的终端里多一条 `GET /api/files.json`；10s 就回来则没有
- 为什么挂在 `ProcessLifecycleOwner` 上，而不是 `MainActivity` 的 `onStop`？（App 有多个 Activity 时，从 A 跳到 B，A 会 `onStop`，但 App 并没有进后台。线上 App 里 H5 容器往往是单独的 Activity）
- Android 切后台后进程还在跑（直到被系统回收），iOS 几秒后就挂起。所以 Android 其实可以用定时器数 30s，但为什么还是推荐「回来时算时间差」？（进程可能被冻结 / 被杀；三端写法统一）
- 🔬 `m3_2_pauseIsNotBackground` 防的是什么？分屏模式下点另一个 App，你的 App 会走到哪一步？

## M3-3 进出组合打日志 · `lifecycle/CompositionLog.kt`

<details><summary>提示 2</summary>

`DisposableEffect(key) { 进入时做的事; onDispose { 离开时做的事 } }`。key 不变时，重组不会重新执行它；key 用 `Unit` 表示「只跟着进出组合走」。直接在函数体里写 `log(...)` 的话，每次重组都会再打一遍。
</details>

<details><summary>答案</summary>

```kotlin
DisposableEffect(Unit) {
    log("$name 进入组合")
    onDispose { log("$name 离开组合") }
}
```
</details>

想一想：
- 对照 Vue：`DisposableEffect(Unit)` ≈ `onMounted` + `onUnmounted`；`DisposableEffect(id)` ≈ `watch(id, ..., { immediate: true })` + `onCleanup`。🔬 把 key 改成 `log`，测试 `m3_3_enterAndLeaveLoggedOnce` 会打出什么？（每次重组 log 都是新对象 → 先 dispose 再重新进入）
- `LaunchedEffect` 也能在进入组合时执行，为什么这里不用它？（没有 onDispose；它是用来启动协程的）
- 「进入组合」≠「显示在屏幕上」：进详情页时 `FileListScreen 离开组合` 了吗？`FileListScreen.lifecycle` 走到了哪一步？（Navigation Compose 默认会把不在栈顶的页面移出组合，但它的 NavBackStackEntry 还活着，所以 ViewModel、`rememberSaveable` 都还在）
- **对工作**：H5 容器页面里，WebView 是在 `AndroidView` 的 factory 里创建的。页面离开组合时 WebView 要 `destroy()`，否则会怎样？（M4 的 `H5Screen` 里就是用 `DisposableEffect` 做的，读一下）

## M3-4 挪到后台线程 · `lifecycle/MainThreadDemo.kt`

先做实验（M3-3、M3-6 填完、STAGE = 3、开着 mock 服务）：🔬 列表页右上角「⋮」

1. 点「主线程 sleep 2s」，立刻去滑列表：滑得动吗？连点几次、等 5s 以上，会弹「应用无响应」（ANR）吗？
2. 点「主线程网络请求」：toast 显示什么？logcat 里 `[M3] thread=` 是什么？
3. logcat 搜 `StrictMode`：第 1、2 步各留下了什么？
4. 填完 M3-4，点「后台网络请求」：`thread=` 是什么？

<details><summary>提示 2</summary>

```kotlin
scope.launch {
    val text = withContext(io) { outcome(work) }
    onResult(text)
}
```

`scope.launch` 立刻返回（只是把协程排进去）；`withContext(io)` 在 io 上跑完以后，自动回到 scope 的调度器（主线程）上继续执行下一行。
</details>

<details><summary>答案</summary>

```kotlin
scope.launch {
    val text = withContext(io) { outcome(work) }
    onResult(text)
}
```
</details>

想一想：
- 🔬 写成 `runBlocking { withContext(io) { ... } }`，`m3_4_returnsImmediately` 会挂。work 确实在 io 上跑了，为什么主线程还是被卡住了？（`runBlocking` 会阻塞当前线程直到里面跑完，等于没挪）
- 🔬 把 `withContext(io)` 去掉，`thread=` 变成什么？对比 JS：`await fetch()` 不阻塞主线程，但这里 `execute()` 是阻塞的；Kotlin 里 `suspend` 只是「可以挂起」，不代表里面的代码不阻塞线程
- 出题时发现：OkHttp 5 默认开着 fast fallback（IPv4 / IPv6 并行连接，连接在 OkHttp 自己的线程上建），mock 服务**没开**时，主线程上看到的是 `ConnectException` 而不是 `NetworkOnMainThreadException`。所以 `MainThreadDemo` 里的 client 关掉了 `fastFallback`。这说明 `NetworkOnMainThreadException` 是怎么检测的？（StrictMode 的 `detectNetwork`：socket 操作发生在主线程上才抛，系统默认给主线程开了这一条，而且是 `penaltyDeath` 级别）
- `enableStrictMode()` 里用的是 `Builder(StrictMode.getThreadPolicy())`。🔬 改成 `Builder()`（从空策略开始），再点「主线程网络请求」：还抛 `NetworkOnMainThreadException` 吗？（出题时在 API 37 上实测：不抛了，请求在主线程上照常发出去、拿到了 HTTP 200。系统默认的 `penaltyDeathOnNetwork` 被新策略整个替换掉，只剩 `penaltyLog`。真实工程里「开 StrictMode 反而让崩溃消失」就是这么来的）
- **对工作**：`@JavascriptInterface` 方法跑在哪个线程？`shouldInterceptRequest` 呢？（都不是主线程，M4 会用到。所以 bridge 里读文件不卡 UI，但要碰 WebView 就得切回主线程）

## M3-6 收到刷新信号就刷新 · `ui/FileListViewModel.kt`

<details><summary>提示 2</summary>

`collect { }` 会一直挂起等下一个值，所以要放进 `viewModelScope.launch { }` 里单独跑。`viewModelScope` 在 ViewModel `onCleared` 时自动取消，收集也就停了。
</details>

<details><summary>答案</summary>

```kotlin
viewModelScope.launch {
    refreshRequests.collect { refresh() }
}
```
</details>

想一想：
- 🔬 换成 `GlobalScope.launch(Dispatchers.Main) { ... }`，`m3_6_subscribedOnce_stopsAfterCleared` 会挂。页面退出以后会发生什么？（ViewModel 泄漏，进程活着的每次回前台都在给一个没人看的页面发请求）
- 另一种写法是在 `App.kt` 里 `LaunchedEffect(vm) { AppLifecycle.refreshRequests.collect { vm.refresh() } }`。旋转屏幕时它会怎样？（Activity 重建 → 重新进入组合 → LaunchedEffect 重启，订阅还是只有一份，但这种逻辑放在 ViewModel 里更不容易出错）
- `refreshRequests` 是 `SharedFlow`，不是 `StateFlow`。如果用 `StateFlow<Unit>`，第二次回前台还能触发吗？（StateFlow 值相同不会重复发；「事件」用 SharedFlow，「状态」用 StateFlow）
- iOS M3-3 是 `loadIfNeeded()` 防重复加载。Android 这边 ViewModel `init { load() }` 天然只跑一次，为什么 iOS 需要额外处理？
