# M5 提示与答案：打包、异常采集

格式和前面不一样：README 说 M5「不留空」，所以代码里只有接口签名、要求和测试，**每个 TODO 都是一整个函数体，注释里没有提示 1**。下面先给方向（相当于提示 1 + 2），再给答案（折叠）。展开过答案的在 `notes/android-M5.md` 记一笔。

## 开始前

- 把 `Stage.kt` 里的 `STAGE` 改成 `5`。STAGE ≥ 5 时：
  - `M3EApplication.onCreate` 里装崩溃钩子（M5-1），并把上次崩溃留下的记录打出来（M5-3）
  - 列表页「⋮」菜单多出三项：崩溃：主线程 / 崩溃：后台线程 / H5 抛错（case=blank）
  - H5 页的 console 消息经过 M5-4 筛选，未捕获异常转到原生日志 `[H5_ERROR]`；页面脚本执行前注入 `H5_ERROR_HOOK_JS`（`WebViewCompat.addDocumentStartJavaScript`，只对离线包 origin）
- M5-1 ~ M5-4 没填时 App 不会因为它们崩（`TodoGuard` 接住了），只是采集不到
- `./check.sh M5` 不到 1 分钟；`m5_4_*` 有两个仪器测试要开模拟器

| 空 | 文件 | 内容 | 检查方式 |
|---|---|---|---|
| M5-1 | `crash/CrashReporter.kt` | 装进程级未捕获异常钩子，处理完交还给旧钩子 | JVM 单测 |
| M5-2 | `crash/CrashReporter.kt` | 处理一个异常：打日志 + 写文件，写失败不能再抛 | JVM 单测 |
| M5-3 | `crash/CrashReporter.kt` | 下次启动报上次的崩溃，只报一次 | JVM 单测 |
| M5-4 | `crash/CrashReporter.kt` | 从 H5 console 消息里认出未捕获异常 | JVM 单测 + 仪器测试 |
| 手工 1–4 | — | 刻意崩溃、release 包、R8 + retrace、体积 | 测不了 |

JVM 单测不会真的让测试进程崩：测试先装一个假的「系统默认钩子」，再直接调你装上的钩子的 `uncaughtException`，看它记了什么、有没有交还。

## M5-1 装钩子 · `crash/CrashReporter.kt`

方向：

- 进程级的钩子是 `Thread.setDefaultUncaughtExceptionHandler`（静态方法，对所有线程生效）。`Thread.currentThread().setUncaughtExceptionHandler` 只管当前这一个线程
- 先用 `Thread.getDefaultUncaughtExceptionHandler()` 把旧的存下来，可能是 null
- 新钩子里先 `handle(thread, e)`，再 `previous?.uncaughtException(thread, e)`。用 `try { } finally { }` 保证 handle 自己出错时也会交还
- 「重复调用只装一次」：类里加一个 `private var installed = false`（写在 install 下面也行，Kotlin 类的成员不分先后）

<details><summary>答案</summary>

```kotlin
fun install() {
    if (installed) return
    installed = true
    val previous = Thread.getDefaultUncaughtExceptionHandler()
    Thread.setDefaultUncaughtExceptionHandler { thread, e ->
        try {
            handle(thread, e)
        } finally {
            previous?.uncaughtException(thread, e)
        }
    }
}

private var installed = false
```
</details>

想一想：
- 🔬 不交还给 `previous`：点「崩溃：主线程」，App 会怎样？（预期：不弹「应用已停止」，主线程已经因为异常结束了，界面冻住，进程不会自己退出。以你实测为准，记进 notes。对比鸿蒙 M5-1：`errorManager.on('error')` 处理完 App 还活着）
- `previous` 是谁装的？🔬 在 install 里打一行 `previous?.javaClass?.name`。（系统的 `RuntimeInit$KillApplicationHandler`；如果你接了 Bugly / Firebase Crashlytics，就是它们的）iOS M5-1 的想一想是同一个问题：多个崩溃 SDK 怎么共存
- 后台线程的崩溃，主线程的 Looper 还活着吗？为什么不交还时也必须杀进程？（状态已经不一致了）
- 协程里没 catch 的异常走的是这个钩子吗？`viewModelScope.launch { throw ... }` 呢？（会，协程没人接的异常最后交给线程的 UncaughtExceptionHandler；`CoroutineExceptionHandler` 是协程这一层的钩子）

## M5-2 处理一个异常 · `crash/CrashReporter.kt`

方向：

- 记录用写好的 `crashRecord(thread.name, e)`，里面是 `e.stackTraceToString()`，带 Caused by
- 写文件用 `file.writeText(...)`（覆盖），外面包 `try { } catch (e: Exception) { log(...) }`
- 为什么还要写文件：进程马上就要死，logcat 是异步刷的，不一定来得及；真实的崩溃 SDK 也是先落盘、下次启动再上报

<details><summary>答案</summary>

```kotlin
fun handle(thread: Thread, e: Throwable) {
    val record = crashRecord(thread.name, e)
    log(record)
    try {
        file.parentFile?.mkdirs()
        file.writeText(record)
    } catch (io: Exception) {
        log("[CRASH] 崩溃记录写入失败：$io")
    }
}
```
</details>

想一想：
- 为什么不在崩溃时直接发网络请求上报？（主线程上会 `NetworkOnMainThreadException`，见 M3；起新线程的话进程可能等不到它发完）
- `catch (e: Exception)` 接不住 `OutOfMemoryError`（它是 `Error`）。OOM 崩溃时还能写文件吗？真实 SDK 怎么做？（预先分配好缓冲区）
- Native（C / C++ `.so`）崩溃是 `SIGSEGV` 之类的信号，这个钩子收不到。对照 iOS M5-2 的信号钩子：Android 上采集 native 崩溃用什么？（Breakpad / Crashpad 生成 minidump；系统的 tombstone 在 `/data/tombstones/`）**对工作**：WebView 渲染进程的崩溃算哪一种？（都不算：是另一个进程，走的是 M4-10 的 `onRenderProcessGone`）

## M5-3 下次启动报上次的崩溃 · `crash/CrashReporter.kt`

方向：没有文件返回 null；有就读出来、打日志（开头要是「[CRASH] 上次运行崩溃了」）、删掉、返回内容。

<details><summary>答案</summary>

```kotlin
fun reportPrevious(): String? {
    if (!file.exists()) return null
    val record = file.readText()
    log("[CRASH] 上次运行崩溃了，现场记录：\n$record")
    file.delete()
    return record
}
```
</details>

想一想：先删再报，还是先报再删？如果「报」是网络上传、上传失败了呢？

## M5-4 认出 H5 的未捕获异常 · `crash/CrashReporter.kt`

方向：

- `H5Container` 的 `WebChromeClient.onConsoleMessage` 把每一条 console 消息都交给你，`isError` 是 `messageLevel() == ERROR`
- 浏览器内核对未捕获异常自己会打一条 error 级别、以 `Uncaught` 开头的消息（只有一行）；`H5_ERROR_HOOK_JS` 会再打一条 `[H5_UNCAUGHT]` 开头、带堆栈的
- 两个前缀用 `startsWith`，不能用 `contains`（业务日志里可能正好带这个词）

<details><summary>答案</summary>

```kotlin
fun h5ErrorLine(isError: Boolean, message: String, source: String, line: Int): String? {
    val uncaught = message.startsWith(H5_UNCAUGHT_BROWSER_PREFIX) || message.startsWith(H5_UNCAUGHT_HOOK_PREFIX)
    if (!isError || !uncaught) return null
    return "[H5_ERROR] $message @ $source:$line"
}
```
</details>

手工验收：🔬 「⋮」→「H5 抛错（case=blank）」，logcat 里有：

```
[H5_ERROR] Uncaught Error: [case=blank] simulated crash before mount @ https://h5.offline.test/app.js:9
[H5_ERROR] [H5_UNCAUGHT] Error: [case=blank] simulated crash before mount
    at https://h5.offline.test/app.js:9:11 ... @ https://h5.offline.test/index.html:1
```

想一想：
- 「Uncaught」那条只有一行，为什么还要注入 `H5_ERROR_HOOK_JS`？为什么必须用 `addDocumentStartJavaScript`，而不是在 `onPageStarted` 里 `evaluateJavascript`？（`case=blank` 在 app.js 一执行就抛，晚了就抓不到；iOS 的 `WKUserScript .atDocumentStart`、鸿蒙的 `javaScriptOnDocumentStart` 是同一件事）
- 🔬 出题时 M4 阶段（bridge 还推当前值时）在 logcat 里见过一条 `[H5_ERROR] [H5_UNCAUGHT] Script error. @ :1`。什么情况下 `window.onerror` 只拿到 `Script error.`？（跨域脚本的错误信息被浏览器隐藏；`evaluateJavascript` 执行的脚本也没有 origin。要 `crossorigin` 属性 + CORS 头）线上 App 的 H5 的错误监控里遇到过吗？
- `addDocumentStartJavaScript` 的第三个参数 `setOf(OFFLINE_ORIGIN)` 是 origin 白名单。和 M4-6 想一想里 `addWebMessageListener` 的白名单是同一个机制。为什么 `addJavascriptInterface` 没有这个参数？（它是 Android 4.2 时代的 API）
- **对工作**：线上 App 的 H5 异常是 H5 自己上报（Sentry 之类），还是 Native 从 console 里捞？两者能对上吗？

## 手工任务 2：release 包

现在 `app/build.gradle.kts` 里 release 是 `optimization { enable = false }`（不混淆、不压缩）。先保持关着打一次：

```sh
cd android
./gradlew assembleRelease
ls -la app/build/outputs/apk/release/
```

没配签名时产物是 `app-release-unsigned.apk`，装不上。学习项目最省事的办法是先用 debug 证书签：在 `release { }` 里加一行 `signingConfig = signingConfigs.getByName("debug")`。真实发版用自己的 keystore（`signingConfigs { create("release") { storeFile = ...; storePassword = ... } }`，密码从环境变量 / `local.properties` 读，不进 git）。

```sh
adb install -r app/build/outputs/apk/release/app-release.apk
```

如果提示签名不一致，先 `adb uninstall com.example.mobile3end`（会清掉 App 数据）。

## 手工任务 3：打开 R8，看混淆后的堆栈，用 mapping.txt 还原

1. 打开优化。出题时实测（AGP 9.2.1）：直接把 `enable = false` 改成 `true`，构建会报 `Cannot use optimization.enable=true without setting android.r8.gradual.support flag`。两种改法：
   - 在 `gradle.properties` 里加 `android.r8.gradual.support=true`，再把 `enable` 改成 `true`
   - 或者换成经典写法（出题时用的是这个，实测能出 mapping.txt）：

     ```kotlin
     release {
         isMinifyEnabled = true
         isShrinkResources = true
         proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"))
         signingConfig = signingConfigs.getByName("debug")
     }
     ```

   （AGP 9 新 DSL 的细节以你的版本文档为准，哪种跑通了记进 notes）
2. `./gradlew assembleRelease`，装到模拟器 / 手机，「⋮」→「崩溃：后台线程」
3. 看 `[CRASH]` 日志，出题时拿到的是这样：

   ```
   [CRASH] 线程 m3e-worker 未捕获异常 ij: M5 刻意抛出的异常：配置解析失败
   ij: M5 刻意抛出的异常：配置解析失败
       at l3.run(r8-map-id-f3fed242...:23)
       at java.lang.Thread.run(Thread.java:1572)
   Caused by: java.lang.NumberFormatException: For input string: "oops"
       at java.lang.Integer.parseInt(Integer.java:779)
       at l3.run(r8-map-id-f3fed242...:14)
   ```

   类名变成了 `ij`、`l3`，`parseConfig` / `readVersion` 两层被内联进了 lambda，文件名变成了 `r8-map-id-<hash>`
4. 还原：把这段堆栈存成 `stack.txt`，用 SDK 自带的 retrace（要能找到 Java，命令行里先 `export JAVA_HOME=...`，同 check.sh）：

   ```sh
   export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
   ~/Library/Android/sdk/cmdline-tools/latest/bin/retrace app/build/outputs/mapping/release/mapping.txt stack.txt
   ```

   出题时还原出来是：

   ```
   at com.example.mobile3end.crash.CrashDemo.parseConfig(CrashDemo.kt:29)
   at com.example.mobile3end.crash.CrashDemo.crashOnBackgroundThread$lambda$1(CrashDemo.kt:22)
   ...
   at com.example.mobile3end.crash.CrashDemo.readVersion(CrashDemo.kt:32)
   ```

   被内联的方法也还原出来了。但出题时异常类名那一行（`ij: M5 刻意抛出的异常`）被还原成了 `kotlinx.coroutines.CompletionHandlerException`，下面又多了一行 `M3EDemoCrash.<init>`：R8 做了类合并 / 内联，同一个短名在 mapping 里可能对应不止一个原名，retrace 只能猜。🔬 在 mapping.txt 里搜 `-> ij:` 看看。带你自己前缀的第一行（`[CRASH] ...`）retrace 不处理
5. 做完把 release 改回原样，或者保留打开的状态、在 notes 里写清楚（后面的 check.sh 只跑 debug，不受影响）

## 手工任务 4：debug 和 release 的体积

```sh
ls -la app/build/outputs/apk/debug/app-debug.apk app/build/outputs/apk/release/app-release.apk
unzip -l app/build/outputs/apk/debug/app-debug.apk | grep -E 'classes.*dex|assets/'
unzip -l app/build/outputs/apk/release/app-release.apk | grep -E 'classes.*dex|assets/'
```

出题时实测（STAGE 不影响体积）：

| 包 | APK 大小 | dex | 文件数 |
|---|---|---|---|
| debug | 约 13.6 MB | 12 个 `classes*.dex`，合计约 33 MB（解压后） | 148 |
| release（R8 + 资源压缩） | 约 1.5 MB | 1 个 `classes.dex`，约 2.3 MB | 99 |

🔬 自己量一遍（关着 R8 的 release 也量一下），把差异和原因写进 notes：

- dex 小在哪：R8 删掉了没用到的类和方法（Compose、OkHttp、协程里你没用到的部分）、改短名字、内联
- debug 为什么有 12 个 dex：debug 构建为了增量编译快，按依赖库分别 dex、不做合并（细节以 AGP 文档为准）
- debug 包里还有什么：`ui-tooling`（Preview 用）、`ui-test-manifest`（`debugImplementation`）
- 对比 iOS：Debug / Release 的差异来自 `-O` 优化和调试 dylib，没有「混淆」这一步；对比鸿蒙：abc 字节码 + sourcemap 不进 release 包

想一想：线上 App APK 里最大的是什么？（通常是 `lib/` 下的 `.so` 和资源。`unzip -l` 自己的 App 看一眼）
